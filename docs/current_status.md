## 已完成功能

- 多账号注册登录、14 天 Cookie 会话、个人健康工作区和个人 API Key。
- 有生效日期的身体资料、可选体脂、每日测量与历史补录。
- 普通照片识餐、包装标签草稿、手工修正、份量换算、确认入账和按周查看历史。
- 删除已结束的餐食分析，保留已入账餐食、原图及已有备份。
- 力量逐组记录、有氧及羽毛球、训练排期、计划转实际训练和确定性消耗计算。
- AI 饮食目标、有氧估算、每日反馈与满足资格后的每周复盘；过期结果与手动重试。
- 固定统计起点、七日体重均值、身体/热量/训练图表。
- 自选受控根目录、位置展示、个人迁移、整根迁移、健康备份与恢复。
- Windows 无 CMD 启停、重启、版本兼容检查及完整便携 ZIP。

实现与验收对应见 [需求](requirements.md)，合约见 [接口](interfaces.md)。AI 功能存在模型误差，人工确认始终保留。

## 版本、目录与 Git 的关系

维护者本机曾保留以下三种工作区角色。公开文档仅使用相对位置，实际克隆目录由使用者决定：

| 角色 | 整理时的状态 | 注意事项 |
|---|---|---|
| 原研发仓库主工作区 | `master`、v0.3.1 | 有原始开发历史，没有公开仓库远端配置；不要误以为这里修改就会更新 GitHub |
| 原研发仓库发布工作区 | `release/v0.4.0` | 与原仓库共享历史，用于构建与验收 Windows 便携版 |
| 独立公开副本 | `main`、v0.4.0 | 对应 [GitHub 仓库](https://github.com/LinZzzzJ/FitTrack)，后续公开开发以此为基准 |

`artifacts/github-public` 是维护者此前选择的公开副本位置，不是克隆项目时必须复建的目录层次。新电脑直接克隆仓库即可得到完整公开工程。

`main` 是可继续前进的开发分支；`v0.4.0` 标签标记公开源码定版位置；Release 附件是对应功能版本经打包和验收后的成品。推送源码不会自动更新已发布 ZIP，也不会升级任何正在运行的服务。现有 CI 只检查和构建前端，不自动发布便携包。

## 已知问题与未验证假设

- Linux 源码重启命令仍使用 Windows 虚拟环境路径；本机能力开关只区分 `local/server`，没有完整区分操作系统。
- 原生目录选择、打开目录、快捷方式、DLL 管理及部分测试依赖 Windows。
- 锁定依赖来自已验证的 Windows 环境，Linux 上能否完整安装和运行尚未检查。
- 某些历史 AI 标签失败缺少原始校验细节，无法还原确切原因；提高输入分辨率不保证 OCR 正确。
- 浏览器残留进程与 FitTrack 之间没有足以覆盖所有个案的因果结论，不得宣称完全解决或确定由应用造成。
- Windows 10、其他 PC/纯净虚拟机、跨操作系统恢复、真实公网部署均有验证缺口。

这些不阻塞文档整理；Linux 平台问题阻塞宣称完整 Linux 支持。详见 [待确认问题](open_questions.md)。

## 下一步推荐顺序

1. 在新的 WSL 克隆中阅读本指南、架构、环境和移植清单，核对分支与未提交修改。
2. 明确后续要“WSL 编辑、Windows 验收”，还是“服务本身在 Linux 运行”；后者需要单独实现平台适配。
3. 用隔离数据根目录重建 Linux Python/Node 环境，先验证依赖、前端和基础 HTTP 流程。
4. 再适配启动、能力、重启迁移及测试；维持 Windows 全套回归，不跳过失败来宣称支持。
5. 只有达到双平台验收后，更新支持声明并另行打包发布。

开始任何数据迁移前必须明确源与目标、停服和备份方案；禁止用正式健康库作为移植试验材料。
