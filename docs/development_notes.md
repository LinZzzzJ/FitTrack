# 开发经验与故障定位

基线 v0.4.0；整理日期 2026-10-20。仅记录对后续开发有价值的故障；每项区分有证据的原因与未能确定的部分。测试总览见 [ACCEPTANCE](ACCEPTANCE.md)。

## 1. 前端更新、后台未重启导致功能缺失和保存失败

- **现象**：页面有新字段，活动选项却无羽毛球；保存力量/有氧提示 `ai_estimate_job_id` 字段错误。
- **已确认原因**：历史常驻 Python 进程加载旧模块，磁盘静态页面已更新。新前端请求被旧模型 `extra=forbid` 拒绝，与字段填写错误不同。
- **修复**：v0.3 增加加载时版本身份、API 修订号、能力、源码变化检测，前端保留表单并阻止不兼容提交；增加正常重启入口。
- **验证**：`test_version_is_public_and_mismatch_prevents_mutation`、重启超时不强杀测试，以及历史正式实例版本核验记录。
- **经验**：源码提交、前端构建、常驻实例更新分开验证；不能用“本地测试通过”推断正式实例已加载新代码。部署也应检查真实地址的 `/api/version`。

## 2. 图片看似裁剪与 AI 识别失败是两类问题

- **现象**：竖图在宽预览框中只见中间区域；AI 又返回无效营养字段。
- **已确认事实**：历史指定原图尺寸与上传原文件哈希一致，原图没有裁剪；早期识图副本等比缩小。UI 的填充展示与原图存储、AI 输入副本是三条独立路径。
- **修复**：预览使用 contain、显示尺寸并可查看原图；AI 副本纠正 EXIF、长边最多4096、JPEG质量92、8 MiB上限，等比缩小不裁边，保留本地原图。
- **验证**：`test_meal_images.py` 检查四角、EXIF、输入体积、原文件不变、结构异常和空识别。
- **不能推导**：分辨率提高不保证反光、小字、食用份量识别正确。原图正常不能证明模型输出必然满足结构校验。

## 3. 包装标签：区分读数、单位与实际食用量

- **现象**：有标签却无法确认、把 kJ 当 kcal、每100g按整包计算，或将照片中的包装数当食用袋数。
- **已确认原因范围**：早期部分失败处于模型结果校验阶段，但没有保存具体 `ValidationError` 字段，无法追溯每次确切缺项。后续成功调用不能证明所有失败都来自同一原因。
- **修复**：v0.3 独立标签模式，读取允许缺项的草稿，用户确认基准与实际份量，`nutrition.label_food` 后端换算；保存餐食时再次计算。
- **验证**：374 kJ/100g、60g≈53.63 kcal、120g≈107.27 kcal，半袋、缺字段、kcal/份与重复确认等见 `test_diet_labels_version.py`。
- **排查顺序**：先查任务模式/版本和安全错误字段，再核对基准/单位/份量。未经授权不重发真实请求，不读取正式资料来复现，不将原始模型内容写入日志。

## 4. 提供方空行保活会使“读取超时”难以解释

- **现象**：请求等待数分钟，页面一直生成中；有字节保活但最终 JSON 尚未返回。
- **证据与处理**：当前 `AIClient.call` 仍请求非流式模型 JSON，但逐字节读取 HTTP 响应；连接10秒、读90秒，并在收到字节时检查累计120秒、限制2 MiB，所有分支释放响应。
- **验证**：`test_keep_alive_whitespace_has_total_wait_limit_and_closes`、超时无自动重试及保活后JSON测试。
- **边界**：累计检查在迭代收到数据时执行，不是独立硬中断计时器；不能承诺所有网络情况下精确120秒结束。提供方可能已消费额度，超时后由用户决定重试。

## 5. 数据变化后，旧 AI 结果不能覆盖新记录

- **现象/风险**：生成目标或反馈期间修改身体参数、备注或饮食；新结果完成时已基于旧输入。
- **处理**：请求前持久化指纹，完成、读取和采用/保存时按任务类型重新核对；旧结果标 `stale`。同周生成失败保留上一份成功周报告。
- **验证**：目标、有氧、周分析和反馈顺序测试分别位于 `test_goal_suggestions.py`、`test_coaching.py`、`test_ai_and_recovery.py`。
- **经验**：`stale` 与 `failed` 不同；不是所有过期结果都应自动重新调用 AI。重启后 pending 变 interrupted，不能后台自动付费重发。

## 6. Windows 文件替换和停服应答存在竞态

- **现象**：多进程短暂读取 JSON 时 `os.replace` 遇到共享冲突；正常停服时连接可能先于 HTTP 应答关闭。
- **修复**：`paths.write_json` 只对指定 Windows 共享错误短暂重试；重启等待原实例状态文件移除和端口释放，不因没有收到停服应答就立即强杀或开第二实例。
- **验证**：受控运行、真实文件占用回归及重启超时测试；成品 Windows 原生流程有历史验收。
- **移植注意**：POSIX 原子替换、权限和 flock 分支仍需 Linux 实测。跨 Windows/WSL 共用根目录不能假设获得同一实例锁。

## 7. 删除分析要解除来源，保留餐食可编辑

- **现象/风险**：直接删除任务会留下餐食 JSON/索引中的关联；编辑时回传 `totals`、`created_at` 等只读字段会被严格模型拒绝。
- **修复**：v0.3.1 在同一事务解除餐食 `source_job_id` 的索引和 JSON 后删除任务；前端编辑使用请求字段。处理任务完成恰逢删除时的通知竞态。
- **验证**：`test_delete_meal_jobs.py` 覆盖归属、运行任务拒绝、回滚、营养不变、恢复与并发边界；历史独立浏览器检查覆盖取消、失败重试、跨页刷新及窄窗口。
- **经验**：删除分析≠删除餐食≠删除照片。用模拟记录验收，不能在正式库上演示不可撤销删除。

## 8. 浏览器残留进程不能直接归因于 FitTrack

- **现象**：用户多次遇到 Edge 后台进程残留，结束某进程后能重新打开浏览器。
- **可确认范围**：有诊断看到普通 Edge 后台/无启动窗口行为；当前启动器不负责结束用户浏览器。冻结程序启动外部进程还需处理 DLL 搜索路径继承，v0.4 为此增加隔离，并对已注册的 Edge/Chrome 显式请求新窗口。
- **未知**：现有材料不能证明所有打不开个案由 FitTrack 造成，也不能证明系统问题已被彻底解决。
- **验证与后续**：`test_portable.py` 验证 DLL/PATH 恢复及浏览器命令；重现时需进程父子关系、命令行、时间线及有/无应用的受控对照。测试只管理自己创建的浏览器配置与进程。

## 9. 冻结 EXE 与源码解释器的运行边界不同

- **风险**：源码中相对 `.venv` 的重启命令在 EXE 不存在；无控制台进程无法可靠从 stdout 读取目录选择结果。
- **修复**：统一 `distribution` 中的安装/资源/子进程路径；目录选择子进程把结果写入根目录 tmp 随机 JSON，读后清理；EXE 子进程重置 PyInstaller 环境。
- **验证**：便携9项测试、`check_portable_release.py`、`check_portable_ui.py` 的历史成品验收。
- **移植注意**：源码启动路径仍固定 Windows `.venv/Scripts`；这是后续 Linux 适配项，不能误认为 EXE 适配已解决跨 OS。

## 10. 文档与工作区混淆会让后续修改失效

- 原开发主工作区、发布 worktree 与独立公开仓库可能版本不同；开始前核对根目录、分支、版本和远端。
- `.gitignore` 排除的运行/开发文件不会随 Git 迁移。公开标签的短哈希与原私人仓库标签不同，是独立历史的结果。
- README 的 `ARCHITECTURE.md` 等文件名大小写必须与磁盘一致；Windows 上“能点开”不足以证明 Linux 正常。
- 优先使用相对链接和明确环境命令，不把维护者绝对路径、正式数据计数或原始日志复制进公开知识库。
