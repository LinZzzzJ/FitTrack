# 项目历史与资料范围

整理日期：2026-10-20；当前公开功能基线 v0.4.0。本文提炼可移植知识，不复制原始聊天、个人记录、私人路径或秘密配置。

## 实际使用的材料与限制

本轮盘点公开仓库的受版本管理文件，重点阅读前后端入口、启动/路径/权限、请求模型、路由、控制/健康存储、凭据、任务、计算/标签、周资格、构建配置及相关测试；同时参考已有 README、架构、进度和验收文档。

可访问历史包括当前会话中展示的用户要求、已批准计划、可访问会话摘要，以及维护者本机原研发仓库的提交说明与历史文档。**这不等于读取了所有历史聊天、全部原始接口响应或每次调试日志。**没有为了知识整理读取正式健康数据库、真实 Key、私人认证文件或原始个人照片。

公开仓库有意从干净 v0.4.0 快照开始，只有初始公开提交起的历史。原研发历史没有推送；本文只提炼其中可公开的设计和验证边界。早期提交不作为新读者必须取得的依赖，当前实现应以公开代码、测试和版本为准。

## 证据标签与冲突处理

| 类型 | 含义 |
|---|---|
| 已确认事实 | 当前代码、配置、明确需求或文档能支持 |
| 已验证方案 | 有明确测试/运行结果，必须保留环境与版本边界 |
| 讨论但未验证 | 曾提出或批准方向，但没有实际成功证据 |
| 当前推断 | 有依据的可能解释，未获得直接验证 |
| 待确认 | 材料缺失或互相冲突，不能得出结论 |

后续明确需求和实际代码优先用于判断当前行为；历史表述冲突仍需保留来源，不能为凑完整而猜测。每次验收的测试数代表对应阶段，不是自动继承到所有平台。当前 Windows 129 项检查结果见 [验收](ACCEPTANCE.md)。

## 主题一：从参考项目到独立健身日记

初始用户希望参考 01 项目的组织方式，建立独立健身减脂网页：身体资料、每日测量、照片识餐、有氧/力量、热量缺口、图表、多账号本地数据库和 AI 建议。视觉要求为米白、深绿、留白和清晰图表。

已采用 Svelte/TypeScript + FastAPI + SQLite，本机同源页面、不可变图片、线程池和 SSE 等组织方式参考 BrushGraft，保留 MIT 声明。未引入其图像编辑/版本树业务。来源：初版需求与实施计划、[当前架构](ARCHITECTURE.md)。

AI 接入曾讨论 ChatGPT Plus 与提供方 API 的关系，随后选择个人提供方 Key。项目默认 DeepSeek 地址和模型名在代码中保留，但外部能力/计费不能仅凭历史对话保证；本知识库不保存任何历史真实 Key 或跟踪标识。

## 主题二：从公共配置到受控根目录和个人凭据

用户先要求后台无 CMD、手动启动、不自启，再明确运行数据不得散落其他磁盘，账号库、密钥、日志、缓存、临时文件、备份和健康记录均需可控。

v0.2 将根目录设为首次选择，控制库与个人健康库分离；Key 改为每账号独立、可记住加密或仅会话内存，没有全局回退。目录不可用不改落其他位置。迁移按复制、核验、切换、保留来源执行。

历史初版 `.env`/单库方案被替代；旧 `Settings` 和导入代码仍存在，不能只搜索到 `.env` 类就判断生产仍使用公共 Key。来源：受控目录批准计划、[credentials](../src/fittrack/credentials.py)、[control](../src/fittrack/control.py)、[决策 D02/D04](decisions.md)。

## 主题三：日期、饮食累加与周复盘逐步明确

用户逐步要求趋势分析、首页和身体曲线统一从 10/15 起；实现固定 `2026-10-15`，分段读取不重置七日均值。固定图表起点不删除历史数据，也不禁止更早日期补录。

训练补充羽毛球，并只对实际有氧提供 AI 估算；平均 MET 覆盖含休息的整次时长，采用与保存分开。周复盘独立于每日反馈，按锚点每七天划分，需周期结束和七天完整饮食/完成标记。首期10/15—10/21在10/22起具备时间资格。

饮食后来增加按周展示、日期分组和补记入口，七天是界面窗口不是保存期限。新增夜宵与晚餐累加，更新既有条目才修改原餐。来源：统一趋势/有氧/周分析及饮食周视图批准计划、[coaching](../src/fittrack/coaching.py)、[需求](requirements.md)。

## 主题四：图片、标签与版本混用故障

照片裁切疑虑推动三路核对：上传原图、界面预览、AI 编码副本。历史证据支持原图未裁，UI 完整展示和高分辨率等比副本后续已实现；这不证明 OCR 必然准确。

包装识别曾多次失败，部分旧错误缺少字段细节，不能还原精确原因。v0.3 增加单独标签流程：AI 读草稿，用户确认基准/单位/份量，后端做 kJ 换算和缩放；未知不填零。不要把“某次分析准确”推导成“当前每次均应准确”。

另一已确认故障是常驻旧后台与新静态页面混用，造成羽毛球选项缺失和新字段被拒绝。后续加入版本身份、兼容保护与正常重启；源码和页面更新后还需核验实际实例。来源：运行版本同步批准计划、历史验收、[故障经验](development_notes.md)。

## 主题五：删除、备份与不可撤销边界

v0.3.1 增加照片/标签分析删除：用户确认后仅删已结束任务，保留餐食、原图和备份；事务解除关联，后续编辑/恢复仍正常。运行任务不能删除。

用户曾询问“上传记录是否都有备份”。应区分日常持久化和独立健康 ZIP 备份：保存即写数据目录，独立备份需主动创建，不是每次上传自动生成一份备份。来源：删除批准计划、当前保存/备份接口及 [使用指南](../README.zh-CN.md)。

## 主题六：Windows 便携成品与浏览器问题

用户希望其他 PC 解压即用，体积小但功能完整，有 TXT/离线 HTML 指南。v0.4.0 采用固定 CPython/PyInstaller、无控制台 onedir ZIP、原生目录选择、独立构建环境及完整依赖；原业务合约保留。

Edge 后台残留曾被多次反馈。已处理外部进程继承冻结 DLL 环境并对 Edge/Chrome 请求新窗口，但现有材料不能确定所有打不开的个案由应用引发，也不能称彻底解决。源码测试和 Windows11 成品验收不等同其他 PC/Win10 实机验收。来源：便携版批准计划、[公开验收](ACCEPTANCE.md)、[待确认问题](open_questions.md)。

## 主题七：GitHub 公开与跨平台接手

用户要求 Public 仓库、精致 README、成品 Release，且不公开个人数据和原私人开发历史。因而建立独立公开副本，使用 `main`，v0.4.0 标签与 Release 分别保存源码定版和可下载成品。公开 README 使用模拟截图。

原工程主分支 v0.3.1、原库发布工作区 v0.4.0、独立公开副本 v0.4.0 是三种工作角色，不自动互相同步。新电脑应克隆公开仓库，而不是复制整个开发产物树；Release 用于直接运行，源码克隆用于开发。

目前用户要求建立可随 Git 迁移的知识库，为 Ubuntu/WSL 开发准备。此需求不等同批准修改业务或直接完成 Linux 适配；本轮没有重写启动、改依赖、移动正式数据或发布新安装包。后续移植见 [migration](migration.md)。
